# 2026-09-05 平台改名 + OpenAIMulti / Anthropic / Responses 三协议支持

## 背景

用户要求两件事：

1. 把平台对外名称从「集市开发者平台 / 开发者平台」改为「**API 开发平台**」。
2. 对外除了 `chat/completions`，还要 **serve `anthropic`（Claude Messages）与 `responses`（OpenAI Responses）**，**显示对应端点**，并做到**完全兼容**：每个协议可配置**独立的一套上游 base_url**（不只是共享 OpenAI 上游做字段转换）。

> 此前的实现是「claude_compat=1 时仅把 Claude 请求转成 OpenAI 打到同一个 OpenAI 上游」，本质是字段映射，不是真正接入 Claude/Codex 原生上游。本次改为「每协议独立上游优先，独立上游未配置时才回退 OpenAI 转换」，从而能真正对接 Anthropic 上游（Claude SDK）与 OpenAI Responses 上游（Codex 等）。

## 结论 / 方案

- **命名**：控制台名牌 `AppShell.vue`、登录页 `LoginView.vue`、`index.html` 统一为「SSE_Market API 开发平台」。历史笔记/docs 不改。
- **模型模型**（`ModelRow`）新增两个字段：
  - `anthropic_base_url`：Anthropic Messages 协议独立上游根（如 `https://api.anthropic.com/v1`）。
  - `responses_base_url`：OpenAI Responses 协议独立上游根（如 `https://api.openai.com/v1`）。
  - 三者互不依赖，均可独立配置；`upstream_base_url` 仍作为 OpenAI chat/embed/image 上游与「回退」兜底。
- **协议出口**（平台对外 `/v1`）：
  - `POST /v1/chat/completions` → OpenAI 上游（`upstream_base_url`）。
  - `POST /v1/messages` → 有 `anthropic_base_url` 则**原生透传**；否则若 `claude_compat=1` 回退 OpenAI 转换；否则 400。
  - `POST /v1/responses` → 有 `responses_base_url` 则**原生透传**；否则若有 openai 上游则 Rewrites→Chat 转换；否则 503。
- **前端展示**：
  - 管理台模型编辑：新增「Anthropic Base URL」「Responses Base URL」两个输入框（chat 类型）。
  - 模型列表/用户卡片：显示 `Anthropic`、`Responses` 徽标；`/v1/messages` `/v1/responses` 端点。
  - 控制台 `KeysView` 的 API 根地址下展示各协议端点（Chat/Claude/Responses/Embed/Image）。

## 改进（同日第二轮）：显式协议开关 + 上游支持检测

### 背景

用户进一步要求：不能只靠「是否配置了独立 base_url」来判定协议是否可用，而要让管理员**显式开启** anthropic / responses 两种协议；开启后能**测试上游是否原生支持该协议**，不支持则平台**自动反代**（把该协议转成 chat 打到上游），而不是只报错。

### 方案

- **模型模型**（`ModelRow`）新增两个开关字段：
  - `anthropic_enabled`：是否对外 serve `/v1/messages`。
  - `responses_enabled`：是否对外 serve `/v1/responses`。
  - 迁移默认 `0`；`upstream_base_url` 仍作为 OpenAI chat/embed/image 上游。
- **协议启用判定**：改为「开关驱动」——`enabledChatProtocols` 由 `anthropic_enabled`/`responses_enabled` 决定（不再看 base_url 隐式启用）。
- **转发方式**（某协议开启后）：
  - 有独立 base_url（`anthropic_base_url`/`responses_base_url`）→ **透传**（原生该协议）。
  - 无独立 base_url → **反代**（该协议→chat 打到 openai 上游）。
- **上游支持检测**：新增 `server/src/services/protocol-support.ts` 与 `POST /api/admin/models/:id/test-protocol` 路由。发一次最小探测请求，判断上游是否返回该协议形状：
  - anthropic：`type=message` + `content[]`；responses：`object=response` + `output[]`。
  - 返回 `{ supported, mode: 'passthrough'|'relay', httpStatus, elapsedMs, message, ... }`。
- **前端**（`AdminView.vue`）：
  - 模型编辑：新增「Anthropic 协议开关」「Responses 协议开关」下拉；开启后显示独立 Base URL 输入框 + 「测试上游是否支持」按钮。
  - 测试结果展示：`✔ 上游原生支持（可透传）` 或 `⚠ 上游不支持（将反代）`，含 HTTP 状态/耗时/说明。

### 验证

- `server`: `npx tsc` 通过；`web`: `npm run build` 通过。
- `server/.e2e-test/run-protocol.mjs` 扩至 9 项全过：
  透传（anthropic/responses）、开关未开→400、反代（anthropic/responses 转 chat）、`test-protocol` 探测 supported→passthrough 与 no-base→relay。

### 说明

- 反代（转 chat）依赖 `upstream_base_url`（openai 上游）；若某协议开关开启但既无独立 base 也无 openai 上游，则 503。
- `claude_compat` 保留：当 anthropic 开关开启且无独立 base 时，走 `claudeRequestToOpenAi` 反代；`claude_compat` 本身不再决定是否 serve。

## 第三轮（同日）：去除重复开关 + 协议连通性测试增强

### 背景

用户在管理台看到「Claude 协议兼容（POST /v1/messages）」与「Anthropic（Claude）协议开关」两个开关，疑为重复；并询问「对应的协议如何测试连通性」。

### 结论 / 改动

1. **去重**：`/v1/messages` 的 serve 与反代均由 `anthropic_enabled` 控制，`claude_compat` 不再承担行为控制（仅残留 `capabilities.claude` 展示）。故从管理台移除冗余的「Claude 协议兼容」下拉，模型列表也去掉该徽标（改用 `anthropicEnabled`）。

3. **前端**：测试按钮移到协议开关行，开关开启即能测；新增未保存模型时需先保存再测；结果容器 class 改 `ok`/`err`。

## 第四轮（同日）：API Key 认证方式全面兼容

## 第五轮（同日）：修复流式 Anthropic SSE 缺 `content_block_stop`

### 背景

Claude-Code（CLI 强制 SSE 流式 `/v1/messages`）对接时「转 7s 无输出直接回提示符」。逐份抓流式返回发现 SSE 序列为：

`message_start → content_block_start → content_block_delta… → message_delta → message_stop`（**缺 `content_block_stop`**）

而 Anthropic 官方协议必须：

`message_start → content_block_start → content_block_delta… → content_block_stop → message_delta → message_stop`

### 根因

`claude-adapter.ts` 的 `openAiStreamChunkToClaude` 在 `finish_reason` 到来时直接发 `message_delta`，没发 `content_block_stop`。Claude-Code 解析器等待 `content_block_stop` 未到，导致流解析失败、整段输出被丢弃、静默退回命令行。

### 结论 / 改动

`claude-adapter.ts`：`openAiStreamChunkToClaude` 在 `finish` 时先发 `content_block_stop`（index 0），再发 `message_delta`、`message_stop`。

### 验证

- `server`: `npx tsc` 通过。
- 单测 `stream-seq`：模拟 OpenAI 流 → 输出完整 Anthropic 序列 `message_start/content_block_start/content_block_delta×2/content_block_stop/message_delta/message_stop`，PASS。
- e2e 扩至 13 项全过：新增「streaming anthropic relay SSE sequence」——流式 `/v1/messages` 反代返回含 `content_block_stop` 且位于 `message_delta` 之前。

> 注意：用户实测的是旧版。此修复需重新部署才能生效。

## 第六轮（同日）：流式 usage（output_tokens）统计

### 背景

用户部署后实测流式 `/v1/messages` 已带 `content_block_stop`，但 `message_delta` 的 `usage.output_tokens` 恒为 0，`message_start` 的 `output_tokens` 也为 0。用户要求「上游没有返回用量时，平台要自己统计」。

### 结论 / 改动

- `claude-adapter.ts` `openAiStreamChunkToClaude` 增加可选 `usageHint { input_tokens, output_tokens }`，`message_delta` 据此填入（无 hint 时兜底 `output_tokens:0`）。
- `proxy.ts` 流式反代循环：新增 `collectedText` 累计输出文本；`output_tokens` 优先用上游真实值（`readUsage().completion`，兼容 OpenAI `completion_tokens` 与 Anthropic `output_tokens`），上游无 usage 时按 `Math.ceil(collectedText.length/4)` 估算。
- `message_start` 起始 `output_tokens` 保持 0（流开始时合理），客户端以 `message_delta` 为准。

### 验证

- `server`: `npx tsc` 通过。
- e2e 13 项全过；流式测试新增断言 `message_delta output_tokens >0`（mock 返回真实 `completion_tokens:3` → 平台填入 3）。
- 无 usage 时走文本估算兜底（collectedText/4）。

## 第七轮（同日）：DSML / antArtifact 标记 -> 结构化 content_block

### 背景

Claude Code 接入 DeepSeek 后出现三个功能级问题：
1. `message_delta.usage.output_tokens` 恒为 0 → 客户端判空丢弃（上轮已修）。
2. 模型输出 `<｜DSML｜tool_calls>`（DeepSeek 原生工具调用标记），被当作纯文本透传，客户端不执行 Bash，直接打印原始标签。
3. 模型输出 `<antArtifact>`（工件标记），被当作纯文本透传，不拉起子代理/不渲染工件。

根因：Claude Code 只识别**结构化 content_block**（tool_use / artifact），不会解析文本里的 DSML/antArtifact 标签。

### 结论 / 改动

- `claude-adapter.ts` 新增 `ClaudeContentStream`（流式状态机）：增量识别 `<[｜|]DSML[｜|]tool_calls>` 与 `<antArtifact>`，输出标准 Claude 事件：
  - DSML：`content_block_start{type:tool_use}` → `content_block_delta{input_json_delta}` → `content_block_stop`；`string="true|false"` 兼容，`\|DSML\|` 特殊 token 前缀。
  - **竖线兼容**：全角 `｜` 与半角 `|` 两种变体均识别（`findDsmlStart/End`、正则 `[｜|]DSML[｜|]`）。
  - antArtifact：`content_block_start{type:artifact,identifier,content_type}` → `content_block_delta{text}` → `content_block_stop`（兼容小写/驼峰变体）。
  - 支持**跨 chunk 拆分**（标签被切成多段）与**截断容错**（未闭合不泄漏为 text）。
- `claudeStreamStartEvents` 增加 `withoutContentBlock`，配合 stream 由 stream 全权管理 content_block 生命周期，避免重复 start。
- `openAiStreamChunkToClaude` 增加可选 `ClaudeContentStream`；finish 时若 `emittedToolUse` 则 `stop_reason=tool_use`（除非 length）。
- `openAiResponseToClaude` + `openAiContentToClaudeBlocks`：**非流式**同样拆 text/artifact/tool_use 块。

### 追加：透传路径（anthropic_base_url）同样做标签重建（第八轮补充）

用户实测：即使模型配置了独立 `anthropic_base_url`（如 DeepSeek 官方 anthropic 端点），`/v1/messages` 走**透传**路径时，上游返回的 `<antartifact>` 原始标签仍被当作纯文本显示。Claude Code 只认结构化块。

- 新增 `ClaudePassthroughSse`：解析透传的 Claude SSE，把 `content_block_delta` 里的 `text_delta` 文本送入 `ClaudeContentStream` 重建规范化 content_block（DSML→tool_use、antArtifact→artifact）；只保留 `message_start/delta/stop`。
- 智能守卫：上游若输出**原生结构化 tool_use**（`content_block_start{tool_use}` + `input_json_delta`），则原样透传，不破坏。
- proxy `/v1/messages` 透传流式路径改为逐 `event:/data:` 解析 + 转换重建。

### 验证

- `server`: `npx tsc` 通过。
- 专项单测 `stream-marker.mjs`：纯文本 / DSML 单块 / antArtifact / DSML 拆两段 / 截断 / 非流式 blocks / **半角 `|` 流式与非流式** / passthrough antArtifact 重建 / passthrough DSML 重建 / passthrough 原生 tool_use 透传，全部 PASS。
- e2e 扩至 17 项全过：新增「DSML → tool_use」（tool name Bash、input.command ls、stop_reason=tool_use、标签不泄漏）、「antArtifact → artifact」（identifier demo、content_type、标签不泄漏）、「透传 antArtifact → artifact」「透传 DSML → tool_use」。

### 修复记录

- `dsmlEndTagLen` 位置参数误传（传了 `dsmlStart` 而非 `dsmlEnd`），导致结束标签长度按 0 计算、残留标签泄漏为文本。已修正，并补齐半角变体下「不泄漏」断言。
- `ClaudePassthroughSse` 早期 `structuredMode` 短路过早在 `content_block_start` 置位，导致原生 tool_use 的 start 事件被吞；已改为「暂存 start，等非 text delta/stop 到达时补发」，原生结构化块完整透传。
