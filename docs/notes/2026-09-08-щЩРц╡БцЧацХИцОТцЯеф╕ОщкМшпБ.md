# 2026-09-08 限流「无效」排查与验证

## 背景

用户反馈「限流无效」。需要定位是代码 bug 还是配置问题。

## 结论：代码闸门有效，问题在配置/语义层

### 1. 代码层实测有效（新增 E2E：`server/.e2e-test/rate-limit.mjs`）

用独立进程 + mock 上游直接压测 `/v1/chat/completions`，模型层配置生效：

- **并发限制**：模型 `max_concurrent=2`，并发发 6 个慢请求 → **恰好 2 个 200、4 个 429**。
- **RPM 限制**：模型 `rpm_limit=3`，连续发 6 个 → **前 3 放行、后 3 个 429**。
- **释放**：并发结束后再次请求 → 200（`close`/`finish` 正确复位）。

即 `enforceRateLimits` 的 RPM/并发拦截逻辑本身是健壮的。

### 2. 前端/后端字段链路正确

- 前端模型/用户/密钥表单字段 `rpmLimit` / `maxConcurrent`，与后端 `admin.ts` / `keys.ts` 保存字段一致。
- 全局限流 `rateLimits.enabled`（boolean）→ `PUT /api/admin/rate-limits` 正确处理（`typeof b.enabled === 'boolean'`）。

### 3. 最可能的真实原因（配置层）

`enforceRateLimits` 第一行是硬开关：

```ts
if (!isRateLimitEnabled()) return true   // enabled=0 → 全放行
```

`isRateLimitEnabled()` 读 `store.rate_limits.enabled`。**管理员在前端「限流」Tab 若把「启用限流」关掉（或生产 store 里 `rate_limits.enabled===0`），则所有 `/v1` 代理请求全部放行**，表现为「限流无效」。这是最常见原因。

> 环境变量 `SSEAPI_RATE_LIMIT_ENABLED`（默认 1）只在**无 store 配置**时兜底；**store 存在时以 store 为准**，环境变量不会覆盖已保存的配置。

## 值得注意的语义缺陷（可能被误判为「无效」）

`buildChecks` 里：

```ts
const anyRpm = checks.some((c) => c.rpm > 0)
const anyConc = checks.some((c) => c.maxConcurrent > 0)
```

「默认值仅在没有任何一层显式设置时兜底」。且默认池 key 为 **`conc:default` / `rpm:default`（全局共享一个桶）**。这带来两个易误解点：

1. **默认池是全局共享的**：若 `default_max_concurrent=2`，所有「三层都设为 0（继承）」的模型**共享**总共 2 并发，而不是每个模型各自 2。用户可能以为是「每个模型独立 2」，看到某模型没被单独限制便以为无效。
2. **单层非 0 会关闭整条链的默认兜底**：若给模型 A 设了 `max_concurrent=100`，任何走模型 A 的请求 `anyConc=true`，则默认值不再兜底**该请求链**；但不同请求互相独立判断，不至于串。真正需要注意的是：**若某用户层设了非 0，其所有请求都不再受 `default_max_concurrent` 兜底**，只受该用户上限约束。

## 生产中如何确认

在部署服务器执行：

```powershell
# 看当前限流开关与默认值
node -e "const s=require('./data/sseapi-store.json');console.log(s.rate_limits)"
# enabled=1 且 default* >0 才生效；enabled=0 即全放行
```

或前端「限流 Tab」查看「启用限流」是否为「是」。
